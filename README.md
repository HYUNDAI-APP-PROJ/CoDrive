# CoDrive

현대자동차그룹 차량용 앱 개발 공모전을 위해 개발하는 Pleos 기반 Android 앱입니다.

## 프로젝트 정보

| 항목 | 내용 |
| --- | --- |
| 조직 | HYUNDAI-APP-PROJ |
| 플랫폼 | Pleos Connect / Android |
| 개발 도구 | Android Studio |
| 현재 상태 | 도메인별 패키지 구성 및 함께 주행 중 네이티브 프론트 시연 |

여러 차량이 함께 여행할 때 그룹 관리, 대열 확인, 음성 대화, 공동 의사결정, AI 추천과 여행 기록을 제공하는 앱을 목표로 합니다.

현재 작업 브랜치에서는 `:app` 단일 모듈의 Java/XML View로 **함께 주행 중** 화면을 실행할 수 있습니다. 차량 최대 3대의 남은 거리·도착 정보·에너지와 요청·음성 참여를 모의 데이터로 표시합니다. 서버·차량 SDK·실제 음성은 아직 연결하지 않았습니다. 아래 기능은 전체 앱의 개발 요구사항입니다.

## 개발 시작하기

```bash
git clone https://github.com/HYUNDAI-APP-PROJ/CoDrive.git
git switch develop
```

Android Studio에서 프로젝트 루트를 열고 Gradle을 동기화합니다. 필요한 JDK, Android SDK 및 Gradle 버전은 프로젝트 설정을 기준으로 사용합니다. `app`을 실행하면 `com.codrive.app.DrivingStatusActivity`가 열립니다. 대기실이 아직 없으므로 이번 화면에는 독립 개발 진입점을 제공합니다.

현재 프론트의 실행 방법, 시나리오, 검증 범위와 Pleos 연결 계약은 [차량 상태 화면 개발 안내](docs/vehicle-status.md)에 정리했습니다.

## 패키지 구조 이해하기

### 도메인과 패키지란?

- **도메인**은 앱이 다루는 업무 영역입니다. CoDrive에서는 그룹 관리, 경로 관리, 음성 대화 등이 해당합니다.
- **패키지**는 관련 코드를 모으는 폴더이자 Java 이름 공간입니다. `com.codrive.group.ui.lobby`는 `com/codrive/group/ui/lobby` 경로에 대응합니다.
- **레이어**는 코드의 역할 구분입니다. 같은 업무 안에서도 화면을 그리는 코드, 데이터를 가져오는 코드, 판단 규칙을 처리하는 코드를 구분합니다.
- **모듈**은 별도로 빌드 설정을 갖는 단위입니다. 현재 모듈은 `:app` 하나이며, 도메인별 패키지가 독립 실행·배포되는 MSA 서비스라는 뜻은 아닙니다.

폴더는 먼저 **어떤 업무인가**로 나누고, 그 안에서 **어떤 역할인가**로 나눕니다. 화면에 여러 업무가 함께 보여도 각 업무의 책임은 유지합니다.

### 현재 실제 패키지 구조

소스 루트는 `app/src/main/java/com/codrive`입니다.

```text
com.codrive/
├── app/                    # 앱 시작점·전체 화면 이동·객체 조립

│   │   ├── waiting/        # 출발 준비·참여 차량·재접속 대기
│   │   └── decision/       # 제안·투표·수락·거절·결과
│   ├── data/               # model·repository·source
│   └── domain/
│       └── usecase/        # 그룹 유지·공동 의사결정 규칙
├── route/
│   ├── ui/                 # 목적지·경유지·내비 반영 상태
│   ├── data/               # model·repository·source
│   └── domain/
│       └── usecase/
├── convoy/
│   ├── ui/                 # 대열·차량 상태·부족 알림
│   ├── data/               # model·repository·source
│   └── domain/
│       └── usecase/
├── voice/
│   ├── ui/                 # 그룹·주변 차량 음성 제어
│   ├── data/               # model·repository·source
│   └── domain/
│       └── usecase/
├── recommendation/
│   ├── ui/                 # AI 요청·장소·코스 추천
│   ├── data/               # model·repository·source
│   └── domain/
│       └── usecase/
├── history/
│   ├── ui/                 # 여행 기록·카드·공유
│   ├── data/               # model·repository·source
│   └── domain/
│       └── usecase/

    ├── location/           # 차량 위치 조회·갱신
    └── speech/             # 공통 STT·TTS 처리
```

각 말단 패키지에는 `package-info.java`가 있습니다. 이 파일은 패키지의 역할을 설명하고 Git에 구조를 남기는 문서이며, 화면이나 기능을 실행하는 클래스는 아닙니다.

`com.codrive.app`은 Java 패키지이고 `:app`은 Gradle 모듈입니다. 이름이 비슷하지만 서로 다른 개념입니다.

### 모든 도메인에 적용할 내부 규칙

모든 도메인에 다음 공통 구조를 사용합니다. 현재 `app`에는 실행 진입점이, `convoy`에는 차량 상태 화면·모의 저장소·비교 규칙이, `voice/data`에는 음성 상태 시뮬레이션이 구현돼 있습니다. 그 외 미구현 패키지는 `package-info.java`로 역할을 설명합니다.

```text
<도메인>/
├── ui/                     # 화면별 UI·ViewModel·UiState
├── data/
│   ├── model/              # 앱 데이터와 외부 응답 모델
│   ├── repository/         # 데이터 조회·변경의 진입점
│   └── source/             # 서버·로컬 저장소·차량 SDK 접근
└── domain/
    └── usecase/            # 복잡하거나 재사용하는 업무 규칙
```

여기서 `group` 같은 최상위 도메인은 **업무 영역**이고, 그 안의 `domain/`은 **업무 규칙을 담는 레이어 이름**입니다.

| 위치·이름 | 쉬운 설명 | CoDrive 예시 |
| --- | --- | --- |
| `ui` | 사용자가 보는 화면과 조작 | 참여 차량 카드, 수락 버튼 |
| Activity·Fragment | Android 화면을 구성하는 코드 | 그룹 참여 화면 |
| ViewModel | 입력을 받아 화면에 보여줄 상태를 준비하는 코드 | 초대 코드 입력 처리 |
| UiState | 화면을 그리는 데 필요한 상태 데이터 | 참여 차량 목록, 로딩 여부, 남은 시간 |
| `data/model` | 데이터를 담는 형식 | 차량 정보, 서버 응답 |
| `data/repository` | 데이터가 어디에 있는지 감추고 조회·변경을 제공하는 창구 | 그룹 조회·참여 요청 |
| `data/source` | 외부 시스템과 실제로 통신하는 코드 | 서버 호출, 차량 연료 정보 조회 |
| `domain/usecase` | 여러 상황을 종합해 판단하는 규칙 | 전원 수락 여부와 연결 상태 판단 |
| `app` | 여러 기능을 연결하는 앱 전체 구성 | 화면 이동, 필요한 객체 생성 |
| `core/ui` | 여러 기능에서 실제로 재사용하는 UI | 공통 버튼·카드·테마 |
| `core/network` | 여러 기능이 함께 쓰는 서버 통신 기반 | HTTP 클라이언트·연결 설정·공통 오류 처리 |
| `core/location` | 여러 기능이 함께 쓰는 차량 위치 데이터 제공 | 위치·측정 시각·정확도 조회와 갱신 |
| `core/speech` | 음성과 텍스트를 서로 변환하는 공통 기능 | AI 요청·그룹 응답의 STT, 안내용 TTS |

예를 들어 그룹 경로 변경 화면은 `group/ui/decision`에 둡니다. 수락 여부 판단은 필요에 따라 `group/domain/usecase`에, 서버와의 응답 교환은 `group/data`에 둡니다. 승인된 목적지와 경유지를 내비게이션에 반영하는 책임은 `route`에 둡니다.

### 공통 기반 기능과 도메인의 경계

`core`는 여러 도메인이 함께 사용하는 기술적 기능을 제공합니다. 각 도메인은 이 기능을 사용해 자기 업무를 처리합니다. 현재 `core`에도 역할 설명 파일만 추가했으며, 통신·위치·음성 SDK나 구현 클래스는 추가하지 않았습니다.

- `core/network`는 통신 설정을 공유합니다. 그룹 참여나 AI 추천 API 호출은 각 도메인의 `data/source`에 둡니다.
- `core/location`은 위치 데이터를 제공합니다. 약 50m 내 주변 음성 참여 여부는 `voice`, 대열 표시는 `convoy`, 추천 위치 활용은 `recommendation`에서 담당합니다.
- `core/speech`는 STT·TTS를 제공합니다. 인식된 텍스트가 수락인지, 장소 추천 요청인지는 각 도메인이 판단합니다. 차량 간 실시간 대화 채널 관리는 `voice`에 둡니다.
- 리더의 30초 재접속 대기와 15초 자동 수락은 `group`의 업무 규칙입니다. 공통 네트워크 제한 시간으로 처리하지 않습니다.
- `core`는 개별 도메인의 화면이나 업무 규칙에 의존하지 않습니다. 모든 공통 상태를 모으는 저장소로 사용하지 않습니다.

### 코드를 배치할 때의 원칙

- 새 코드는 먼저 소유 도메인을 정하고, 그 안에서 역할에 맞게 배치합니다.
- `decision`은 그룹에서만 사용하는 기능이므로 독립 최상위 패키지로 만들지 않습니다.
- 한 화면의 UI·ViewModel·UiState·목업 데이터는 같은 화면 패키지에 모읍니다. 화면 수가 늘면 `ui/<화면명>/`으로 나눕니다.
- 화면과 ViewModel은 서버·저장소·차량 SDK를 직접 호출하지 않고 Repository를 사용합니다. 복잡한 규칙에만 UseCase를 추가합니다.
- ViewModel은 Activity·Fragment·View를 보관하지 않습니다.
- Data 레이어는 UI에 의존하지 않습니다. 외부 SDK 타입과 응답 형식은 Data 레이어에서 앱 모델로 변환합니다.
- 다른 도메인의 화면이나 ViewModel을 직접 가져다 쓰지 않습니다. 필요한 데이터·결과·명시적인 호출 경계로 연결합니다.
- 공통 UI는 상태와 이벤트 콜백을 전달받습니다. 특정 도메인의 업무 규칙은 `core`로 옮기지 않습니다.
- 도메인 전체의 재접속·투표·음성 상태는 향후 해당 도메인의 데이터·업무 계층에서 관리합니다. 개별 화면이 사라졌다는 이유로 그룹이 해산되지 않도록 합니다.
- 구현을 단순 전달하는 UseCase나 불필요한 인터페이스·구현체 쌍은 추가하지 않습니다.

XML 화면 리소스는 Java 패키지 밖의 `app/src/main/res`에 둡니다. 예를 들어 `layout/activity_group_lobby.xml`, `drawable/ic_group.xml`, `values/strings.xml`을 사용합니다. 리소스는 그룹별 Java 폴더에 자동으로 나뉘지 않으므로 이름으로 소유 기능을 구분합니다.

## 기능별 요구사항

아래 내용은 초기 기획안과 팀 논의로 정리한 개발 대상입니다. 현재 구현 완료 목록이 아닙니다.

### 1. 그룹 관리·공동 의사결정 — `group`

- 여행 그룹 생성, 초대 코드 발급·입력과 차량 참여.
- 참여 차량·탑승 인원·출발 준비 상태 확인.
- 그룹 리더와 일반 제안의 의사결정 방식 설정.
- 일반 차량이 직접 나가면 해당 차량만 탈퇴.
- 리더가 직접 나가면 그룹 전체 해산 및 그룹 음성 채널 종료.
- 리더의 일시적인 연결 끊김은 직접 탈퇴와 구분하고, 30초간 재접속 대기. 30초 안에 복귀하면 유지하고, 복귀하지 않으면 해산.
- 휴식·식사·정차·방문 장소 제안과 응답 현황·결과 공유.
- 일반 제안은 설정한 다수결 또는 리더 결정 방식 사용.
- 그룹 전체 경로 변경은 대상 차량 전원의 수락이 필요하며, 15초 무응답은 자동 수락으로 처리.
- 버튼 또는 음성으로 수락·거절. 한 차량이라도 거절하면 해당 경로 변경은 적용하지 않음.
- 제안을 받지 못한 연결 끊김 차량은 자동 수락하지 않고 전체 경로 변경 보류. 보류의 최대 시간과 이후 처리는 미정.

### 2. 목적지·내비게이션 — `route`

- 개인·그룹 목적지와 경유지 설정·공유.
- 공동 결정 또는 AI 추천 결과를 내비게이션에 반영.
- 경로 자동 적용 ON: 추천 후 즉시 경로 설정.
- 경로 자동 적용 OFF: 추천 결과를 선택한 뒤 설정.
- 그룹 전체 경로 변경에는 `group`의 전원 수락 규칙 적용. 자동 적용 토글과 그룹 승인 절차를 결합하는 세부 동작은 추가 확정.
- 차량별 실제 내비 반영 성공·실패를 확인하는 처리는 구현 시 검증할 항목.

### 3. 대열·차량 상태 — `convoy`

- 참여 차량의 상대 위치, 차량 간 거리와 이동·정차 상태 표시.
- 연료·배터리 공유는 부족한 차량에 대한 알림을 중심으로 구성.
- 상세 잔량을 항상 표시할지, 부족 기준과 반복 알림 간격은 미정.
- 초안의 선택 기능: 차량 간 거리 이탈·정차 알림, 휴게소까지 거리, 공동 목적지 도착 예정 시간.

### 4. 음성 대화 — `voice`

- 그룹 음성은 인터넷 기반이며, 같은 그룹 차량만 참여하고 차량 간 거리 제한은 없음.
- 주변 음성은 기능을 켠 차량끼리 약 50m 내에서 자동 참여하는 것을 목표로 함. 현재 구현 기준은 인터넷 기반이며, 근거리 직접 통신은 별도 검증 전까지 채택하지 않음.
- 차량별 대화 소리 켜기·끄기와 마이크 음소거 제공.
- 두 채널 동시 참여 시 송신 대상·수신 우선순위, 같은 차량의 중복 음성 처리 방식은 미정.
- 연결 상태 표시와 재접속 처리 필요. 실제 차량의 마이크 접근과 오디오 동작은 Pleos 환경에서 검증.

### 5. AI 장소·코스 추천 — `recommendation`

- 개인과 그룹 모두 사용.
- 텍스트 프롬프트 또는 STT(Speech-to-Text, 음성을 텍스트로 변환)로 요청.
- 맛집·데이트 코스·식사·휴식 장소와 방문 순서 추천.
- 공동 방문 결정은 `group`, 내비게이션 반영은 `route`에서 담당.
- TTS(Text-to-Speech)는 텍스트를 음성으로 읽는 기능으로 STT와 구분. AI 응답 음성 읽기의 구체 범위는 미정.

### 6. 공동 여행 기록 — `history`

- 함께 이동한 거리, 방문 장소와 공동 결정 기록.
- 여행 종료 후 하나의 여행 카드 생성.
- 기록 저장·조회 및 참여자와 공유.
- 여행 종료 조건, 그룹 해산과 기록 저장의 관계는 미정.

## 확정 정책 요약

| 상황 | 현재 합의 |
| --- | --- |
| 일반 차량의 직접 탈퇴 | 해당 차량만 탈퇴 |
| 리더의 직접 탈퇴 | 그룹 전체 해산, 그룹 음성 종료 |
| 리더의 연결 끊김 | 30초 대기, 시간 내 복귀 시 유지, 미복귀 시 해산 |
| 그룹 음성 | 인터넷 기반, 거리 제한 없음 |
| 주변 차량 음성 | 약 50m, 기능을 켠 차량끼리 자동 참여, 현재 인터넷 기반 |
| 그룹 전체 경로 변경 | 전원 수락, 15초 무응답 자동 수락 |
| 한 차량이라도 경로 변경 거절 | 해당 변경 취소, 기존 경로 유지 |
| 연결 끊김으로 제안 미수신 | 자동 수락하지 않고 변경 보류 |
| AI 추천 사용 범위 | 개인·그룹 모두 |
| 경로 자동 적용 토글 | ON은 자동 설정, OFF는 추천 결과 선택 후 설정 |

통신 SDK와 서버 기술은 아직 선정하지 않았습니다. 30초와 15초는 앱의 서비스 정책이며, 특정 SDK의 기본 제한 시간을 의미하지 않습니다.

## 추가로 확정할 사항

다음은 검토 의견이며, 확정 정책과 구분합니다.

1. **자동 적용과 그룹 승인:** 개인 자동 적용은 즉시 진행하고 그룹 전체 변경은 승인 후 반영하는 방식을 제안합니다. 토글이 개인별인지 그룹 공통인지도 정해야 합니다.
2. **응답 시간과 연결 끊김:** 15초를 제안 수신·안내 시점부터 계산하는 방식을 제안합니다. 일반 차량의 재접속 대기 시간, 보류 최대 시간, 투표 중 참여·탈퇴·연결 끊김 시 대상 차량 처리도 정해야 합니다.
3. **50m의 의미:** 위치 오차와 오래된 위치를 고려한 참여·이탈 기준이 필요합니다. A–B와 B–C는 각각 40m지만 A–C는 80m인 경우, 모두 같은 채널인지 각 차량의 50m 내 음성만 허용할지 정해야 합니다.
4. **음성 우선순위:** 그룹·주변 채널의 송신 대상과 수신 방식, AI 음성 입력 중 대화 송신 여부, 내비 음성 안내와의 관계를 정해야 합니다. 송신 채널과 마이크 상태를 사용자가 구분할 수 있어야 합니다.
5. **내비 반영 실패:** 전원 수락과 실제 설정 성공은 별개입니다. 같은 목적지·경유지·방문 순서를 공유하되, 차량별 반영 실패·재시도 처리가 필요합니다. 실제 안내 도로까지 완전히 동일하게 만들지는 별도 요구사항입니다.
6. **해산 이후:** 그룹 음성과 공동 제안은 종료하되 기존 내비 안내와 저장된 기록은 유지하는 방식을 제안합니다. 여행의 명시적 종료와 비정상 해산을 구분할지도 정해야 합니다.
7. **제안과 추천의 유효성:** 동시에 여러 경로 변경이 들어오는 경우의 순서와 취소, 실제 장소·좌표·방문 가능 여부 확인, 잘못된 STT 결과 수정 방법을 정해야 합니다.
8. **공개 주변 음성과 데이터 공유:** 처음 사용할 때의 참여 동의, 특정 차량 음소거·차단, 위치·음성·여행 기록의 저장과 공유 범위를 정해야 합니다. 음성 녹음은 현재 요구사항에 포함되지 않습니다.

목업에서는 정상 화면 외에도 리더 재접속 대기, 수락 카운트다운, 변경 보류·거절·실패, 마이크·수신 음소거 상태를 표현해 규칙을 확인합니다.
